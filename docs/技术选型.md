## 2. 目标与约束

### 2.1 核心目标

1. **低资源、易部署**：优先使用纯 Go 依赖和单二进制交付。
2. **规则可验证**：游戏规则与 Telegram、SQLite、系统时间等副作用隔离，可进行确定性测试。
3. **同房间严格有序**：玩家操作、阶段超时和管理操作不能并发修改同一房间状态。
4. **抗 Telegram 限流**：游戏引擎不直接发送消息，由统一 Outbox 排队、限速和重试。
5. **不为未确定需求过度设计**：不引入微服务、外部消息队列、完整事件溯源、Web 管理后台或对局恢复系统。
6. **部署环境可迁移**：先在本机 Linux/ARM64 开发，最终生产服务器暂不绑定。

### 2.2 已确定的容灾边界

- 对局状态不跨 Bot 进程重启恢复。
- 重启后，未结束对局统一中止，通知参与玩家并保留中止记录。
- 玩家、积分、战绩、战报和中止记录属于长期数据，必须持久化。
- 只持久化中止清场所需的最小活跃局信息，不持续保存完整游戏状态。

## 3. 技术栈总览

| 领域 | 最终选择 |
|---|---|
| 开发语言 | Go 1.25 |
| 构建模式 | 正式产物 `CGO_ENABLED=0` |
| Telegram 框架 | `github.com/go-telegram/bot` |
| Update 接收 | Long Polling 为主，接入边界预留 Webhook |
| 应用形态 | 单进程、单二进制、模块化单体 |
| 数据库 | SQLite |
| SQLite 驱动 | `modernc.org/sqlite` |
| 数据访问 | `database/sql` + `sqlc` |
| 数据迁移 | 纯 SQL migrations |
| 多语言 | `go-i18n/v2` + `go:embed` |
| 日志 | Go 标准库 `log/slog` |
| 测试 | `testing`、Fuzz、Fake Clock、`httptest`、SQLite 集成测试、Race Detector |
| CI/CD | GitHub Actions + GitHub Releases + GHCR |
| 发布产物 | Linux amd64/arm64 原生二进制为主，Docker 为辅 |

选择 `go-telegram/bot` 的主要原因是 API 边界薄、零第三方依赖、原生支持 Long Polling、Webhook 和中间件，便于项目自行掌握房间状态机与发送调度。选型时该项目仍在活跃维护，`v1.23.0` 已支持 Telegram Bot API 10.2。[1][2]

### 3.1 版本策略

- `go.mod` 声明 `go 1.25.0`。
- CI 使用最新 `1.25.x` 补丁版本，不使用会自动漂移的 `latest`。
- 第三方依赖的精确版本在初始化工程时解析并写入 `go.mod`、`go.sum`。
- 正式构建和交叉编译使用 `CGO_ENABLED=0`。
- Race Detector 作业在 CI 原生 Linux 环境单独运行，可为该测试作业启用 CGO；这不改变正式发布产物的纯 Go 构建约束。

## 4. 总体架构

```text
Telegram Update
      │
      ▼
Telegram Adapter ──► Update 去重与路由
      │
      ▼
Room Manager ──► Room Actor（每个活跃房间一个 goroutine）
                      │
                      ▼
                Game Reducer
          State + Command → State + Effects
                      │
          ┌───────────┼────────────┐
          ▼           ▼            ▼
       Outbox       Timer       Storage
          │           │            │
          ▼           └──Command───┘
   Telegram Bot API          SQLite
```

### 4.1 进程模型

- MVP 只有一个应用进程和一个 Go 二进制。
- Bot 接入、房间管理、游戏引擎、Outbox、SQLite、健康检查位于同一进程。
- 模块通过明确接口连接，不通过拆进程制造边界。
- MVP 不使用 Redis、RabbitMQ、Kafka 或独立 worker。
- 后续只有在真实容量数据证明单进程成为瓶颈后，才评估拆分。

### 4.2 Update 接入

- MVP 实际运行方式为 Long Polling。
- 业务模块不直接依赖 Long Polling 循环，而是接收统一的领域输入。
- 接入边界预留 Webhook 配置与适配位置，但 MVP 不同时维护两套生产接入链路。
- Webhook 的实际启用、公网 HTTPS、域名和反向代理在确定生产环境后再决定。

## 5. 游戏引擎

### 5.1 强类型显式状态机

游戏阶段、子阶段、角色、阵营、玩家状态、命令和副作用均使用 Go 类型显式表达，不以自由字符串驱动核心规则。

核心接口遵循以下语义：

```text
新状态 + Effects = Reduce(旧状态, Command)
```

Reducer 的约束：

- 不直接调用 Telegram API。
- 不直接访问 SQLite。
- 不读取系统时间。
- 不创建真实计时器。
- 不读取全局随机源。
- 对非法阶段、无权限玩家、死亡玩家和过期操作返回明确拒绝结果。

外层执行 Effects，例如：

- 发送或编辑消息；
- 启动、替换或停止阶段计时器；
- 写入最小活跃局记录；
- 事务化保存战报和积分；
- 生成需要回到房间 Actor 的完成事件。

本项目不采用完整 Event Sourcing。战报只记录产品需要的领域事件，不把所有内部命令当作永久事件流。

### 5.2 随机源

- 生产环境统一使用 `crypto/rand`。
- 发牌采用无偏 Fisher–Yates 洗牌。
- 随机房间码也使用 `crypto/rand`，并在数据库层保证当前唯一。
- 核心引擎依赖可注入的 `RNG` 小接口；测试使用固定或脚本化随机源。
- MVP 不实现随机种子公开、哈希承诺或多人共同种子协议。

### 5.3 AI 扩展边界

MVP 不接入规则 AI 或 LLM，只预留 `PlayerController` 抽象：

- `HumanController` 将真人输入转成领域 Command。
- 后续 `AIController` 只能读取该 AI 角色依法可见的视图，并输出同一种领域 Command。
- `internal/game` 不得导入 OpenAI、DeepSeek 或其他模型供应商 SDK。
- AI 提示词、策略、模型与超时控制在 AI 玩法 Q&A 完成后单独选型。

## 6. 房间并发与计时

### 6.1 每房间一个 Actor 式事件循环

- 每个活跃房间由一个 goroutine 独占其可变状态。
- 玩家发言、按钮回调、投票、角色技能、阶段超时和房主管理操作全部转换成 Command 后进入该房间 channel。
- 同一房间内严格按接收顺序串行处理，不在多个 handler 中直接加锁修改状态。
- 不同房间可以并行运行。
- 不引入第三方 Actor 框架。

### 6.2 阶段计时器

- 每个房间维护当前阶段所需的 `time.Timer`。
- 每次阶段切换递增 `phaseVersion`。
- Timer 到期后只投递包含 `roomID`、阶段和版本的 Timeout Command。
- Actor 收到 Timeout Command 后再次校验当前阶段与 `phaseVersion`。
- 已停止但仍竞争触发的旧 Timer、网络延迟到达的旧操作和旧按钮回调都会因版本不匹配被拒绝。
- 测试通过可注入 Clock 驱动，不真实等待 10、15、30 或 60 秒。

## 7. Telegram 消息与回调

### 7.1 进程内 Outbox

游戏引擎和房间 Actor 不直接执行 Telegram 网络请求，而是产生待发送 Effect，由 Outbox 统一调度。

Outbox 必须具备：

- 按 Telegram Chat 维持 FIFO；
- 全局限速与单聊天限速；
- 关键消息与普通滚动更新的优先级；
- 对尚未发送的低优先级阶段更新进行合并或覆盖；
- 识别 Telegram `429 RetryAfter` 并按服务端建议延迟重试；
- 对超时、临时网络错误和永久错误分类处理；
- 输出队列长度、失败、重试和 429 计数。

Outbox 保存在内存中，不做 Redis/RabbitMQ 持久化。进程重启时当前对局本来就会中止，因此不为未结束消息单独建设跨重启恢复链路。

### 7.2 MarkdownV2

所有富文本消息统一使用 Telegram MarkdownV2。

硬性约束：

- 动态昵称、房间名、玩家发言和其他用户输入必须经过统一 MarkdownV2 escaper。
- 业务代码不得自行拼接转义字符。
- 本地化文案通过统一 Renderer 生成，发送前进行必要验证。
- 玩家原文只作为转义后的文字插入，不允许注入 MarkdownV2 格式。
- 不在不同消息中混用 HTML 与 MarkdownV2 ParseMode。

### 7.3 按钮回调与幂等

- `callback_data` 使用短的不透明随机 Token，不直接编码房间、身份、目标等业务信息。
- Token 在房间状态中映射到允许用户、动作、目标、阶段和 `phaseVersion`。
- 阶段切换时旧 Token 整体失效。
- Actor 仍需校验操作者、存活状态、角色权限、目标合法性和当前阶段。
- 可反复修改选择的阶段，Token 不简单“一次点击即销毁”，而是按规则覆盖最终选择。
- 使用 Telegram `update_id` 进行有界去重，避免 Long Polling 重连或未来 Webhook 重投造成重复执行。

### 7.4 回调令牌与去重容量策略

- `CallbackManager` 与 `Deduper` 均为**有界内存**（默认容量 1024），超限淘汰最旧：
  - Token：导演在**阶段切换时对旧阶段 Token 整体失效**（`InvalidatePhase`），
    使令牌表占用随阶段推进回落，避免多玩家×多按钮挤掉未处理轮次令牌；
  - Update 去重：有界窗口 + 单调 high-watermark，历史 ID 永不重放；被淘汰后
    再次到达的旧 update 由领域命令幂等（`Processed` 集合）兜底。
- 容量常量集中在 `internal/app/build.go`（`defaultCallbackTokenCapacity` /
  `defaultDeduperCapacity`），如多人局实测不足可单点调大。

## 8. SQLite 与持久化

### 8.1 数据访问栈

- 驱动：`modernc.org/sqlite`，保持纯 Go 和无 CGO 交叉编译能力。
- 接口：标准库 `database/sql`。
- 查询：使用 `sqlc` 从 SQL 生成类型安全的 Go 代码。
- 迁移：保留为可审查的纯 SQL migration 文件。
- `sqlc` 生成的 Go 文件提交到 Git；CI 重新生成并检查工作树必须无变化。

### 8.2 数据边界

长期持久化的数据包括：

- Telegram 玩家账号映射与游戏昵称相关信息；
- 积分；
- 分角色胜负场次；
- 总场次；
- 对局与玩家结算；
- 战报；
- 中止记录；
- Telegram 静态资源 `file_id` 缓存。

进行中房间只保存中止清场所需的最小关系数据，概念上包括：

- `active_rooms`：房间、当前对局、生命周期状态、创建与开始时间；
- `active_room_players`：参与者 Telegram ID、座位号、是否仍在房等通知所需信息。

不持久化：

- 每一步投票与技能选择后的完整 Reducer 状态；
- 用于重启续局的角色、药品、阶段计时和按钮 Token 全量快照；
- 完整内部 Command 事件流。

### 8.3 事务与启动清场

- 建房、入房、退房和开局时同步维护最小活跃记录。
- 正常结束时，在事务中写入战报、积分与统计，并清除 active 标记。
- 启动时扫描遗留 active 记录，标记为“服务重启中止”，生成中止记录并通知可联系的参与者。
- 中止局不判胜负、不加减积分、不计入胜负场次。

### 8.4 SQLite 运行参数

- 启用 WAL。
- 启用外键约束。
- 设置合理的 `busy_timeout`。
- 关键结算使用显式事务。
- 具体连接池上限和同步级别在实现阶段通过集成测试与目标文件系统验证后固化配置。

### 8.5 备份与恢复

应用提供安全的 CLI 能力：

```text
werewolf backup --output <path>
```

备份要求：

- 使用 SQLite 在线备份能力生成一致性快照，不直接复制正在运行的 WAL 主文件。
- 提供离线恢复流程。
- 恢复后执行 SQLite 完整性检查。
- 备份调度、保留周期、压缩、加密和远端同步由未来部署环境负责。
- 应用不内置 S3、WebDAV 或 rclone 供应商逻辑。

## 9. 配置、密钥与本地化

### 9.1 配置

- `config.yaml` 保存数据库路径、运行模式、监听地址、默认语言、Outbox 参数和其他非敏感系统设置。
- 环境变量保存 `TELEGRAM_BOT_TOKEN`、Webhook Secret 等敏感值，并可覆盖对应配置。
- 本地开发允许使用不提交 Git 的 `.env`。
- 启动时对所有关键配置进行显式校验；缺失或非法时直接报错退出。
- 房主可修改的游戏规则存入房间/对局数据，不与应用系统配置混用。
- 不引入 Viper/Cobra 式大一统配置框架；CLI 使用轻量、明确的命令入口。

### 9.2 多语言

- 使用 `go-i18n/v2`。
- 语言资源通过 `go:embed` 内嵌进二进制。
- MVP 只交付 `zh-CN`。
- Reducer 产生语义化消息 key 与参数，不直接拼中文。
- 房间语言属于房间配置并进入游戏上下文。
- 后续英语、日语、韩语、俄语通过新增语言资源扩展，不修改核心规则。

## 10. 静态资源

角色卡图片继续存放在：

```text
assets/role-cards/
```

交付与发送方式：

1. 构建时使用 `go:embed` 内嵌 PNG，原生部署不依赖外部 assets 目录。
2. 某张图片首次发送时上传 Telegram。
3. 将 Telegram 返回的 `file_id` 保存进 SQLite。
4. 后续优先使用 `file_id` 发送。
5. 缓存键包含 Bot ID 与资源内容哈希。
6. 更换 Bot Token 或修改图片内容后，旧缓存自动失效并重新上传。

## 11. 日志、健康检查与指标

### 11.1 日志

- 使用 Go 标准库 `log/slog`。
- 开发环境输出易读文本，生产环境输出 JSON。
- 常用字段包括 `room_id`、`game_id`、`phase`、`phase_version`、`command` 和错误分类。
- 默认不记录 Bot Token、Webhook Secret、完整私聊文本和隐藏身份内容。
- 调试日志也必须遵守身份保密与密钥脱敏规则。

### 11.2 健康检查

可选 HTTP 服务仅提供运行状态接口：

- `/healthz`：进程存活；
- `/readyz`：配置、数据库和 Telegram 接入已达到可服务状态。

MVP 不提供 Web 管理页面或管理 API。

### 11.3 轻量计数器

至少统计：

- 活跃房间数；
- Outbox 队列长度；
- Telegram 发送成功与失败数；
- 429 次数与重试数；
- 阶段超时 Command 次数；
- 被拒绝的过期 Command/Token 数量。

MVP 不绑定 Prometheus Server、ELK 或 OpenTelemetry Collector；后续可在不修改核心业务的前提下接入。

## 12. 代码组织

采用按领域模块组织的 Ports & Adapters，并使用普通构造函数手动注入依赖：

```text
telegram-werewolf/
├── cmd/
│   └── werewolf/              # 程序入口、启动、优雅退出、CLI
├── internal/
│   ├── game/                  # 纯状态机、Reducer、Command、Effect
│   ├── room/                  # Room Actor、计时器、生命周期
│   ├── telegram/              # Update 接入、回调、消息渲染
│   ├── outbox/                # FIFO、限速、合并、重试
│   ├── storage/               # sqlc、事务、Repository 实现
│   ├── player/                # Human/未来 AI Controller 抽象
│   ├── i18n/                  # go-i18n 与 MarkdownV2 Renderer
│   ├── config/                # YAML、环境变量、校验
│   └── observability/         # slog、健康检查、计数器
├── migrations/               # SQLite migration SQL
├── queries/                  # sqlc 查询 SQL
├── assets/
│   └── role-cards/            # go:embed 角色卡图片
└── docs/
```

依赖规则：

- `internal/game` 不导入 Telegram、SQLite、配置、日志或模型供应商 SDK。
- 外层适配器依赖核心领域，核心领域不反向依赖外层。
- 只在确有多个实现或测试替身需求的边界定义小接口。
- 在 `cmd/werewolf` 入口使用普通构造函数组装依赖。
- 不引入 Google Wire、Uber Fx 等依赖注入框架。
- 不机械套用四层 Clean Architecture，不制造无业务价值的 DTO 和空壳接口。

## 13. 测试策略

### 13.1 Reducer 单元测试

- 使用表格驱动测试覆盖阶段流转、角色技能、平票、死亡链和胜负判定。
- 对同一输入与注入依赖保证确定性输出。
- 非法命令必须明确拒绝且不得部分修改状态。

### 13.2 Fuzz 测试

对随机 Command 序列检查：

- 不得 panic；
- 不得重复结算；
- 不得出现非法阶段；
- 不得让死亡玩家执行无权操作；
- 玩家、角色和存活集合满足核心不变量。

### 13.3 Actor 与 Timer 测试

- 使用 Fake Clock，不真实等待阶段时长。
- 覆盖 Timer 取消与到期竞争。
- 覆盖旧 `phaseVersion` Timeout Command 被拒绝。
- 覆盖同房间事件串行和不同房间并行。

### 13.4 SQLite 集成测试

- 每个测试使用临时数据库。
- 从空库真实执行全部 migrations。
- 覆盖正常结算事务、中止清场、唯一约束、外键和并发写入。
- 覆盖备份、恢复与完整性检查。

### 13.5 Telegram Adapter 测试

使用 `httptest` 模拟 Telegram Bot API，覆盖：

- Long Polling Update；
- 发送与编辑消息；
- MarkdownV2 动态值转义；
- 429 与 `RetryAfter`；
- 网络超时、临时错误和永久错误；
- 同聊天 FIFO；
- 更新合并；
- 回调 Token 与重复 `update_id`。

### 13.6 真实 Bot 冒烟

真实 Telegram 测试 Bot 仅用于发布前人工冒烟，不进入普通 CI，避免网络、账号和 Telegram 服务状态导致流水线不稳定。

## 14. CI/CD 与发布

### 14.1 平台

- 源码与 PR：GitHub；
- CI：GitHub Actions；
- 二进制发布：GitHub Releases；
- 容器仓库：GHCR。

当前本地仓库尚未绑定远端；创建 GitHub 仓库与配置远端属于后续执行步骤。

### 14.2 PR 质量门禁

每个 PR 必须通过：

```text
gofmt
go vet ./...
golangci-lint
govulncheck ./...
go mod verify
go test ./...
go test -race ./...
SQLite migrations 从空库执行
sqlc generate 后工作树无变化
linux/amd64 交叉编译
linux/arm64 交叉编译
```

说明：

- `golangci-lint` 与其他 CI 工具使用固定版本。
- `go test -race` 在原生 Linux CI job 中运行。
- 发布构建始终使用 `CGO_ENABLED=0`。

### 14.3 发布产物

原生二进制是主交付形式：

- `linux/amd64`；
- `linux/arm64`；
- 校验和文件；
- systemd unit 模板；
- 配置示例与数据库目录说明。

Docker 是辅助交付形式：

- 本机开发不安装 Docker、不构建镜像；
- 普通 PR 不构建、不推送镜像；
- tag/release 时由 GitHub Actions 使用 Buildx 构建多架构镜像；
- 镜像推送到 GHCR；
- SQLite、配置和日志使用外部挂载目录，不写死在镜像层。

## 15. 明确不采用的方案

MVP 不采用：

- Python、TypeScript/Node.js 作为核心运行时；
- PostgreSQL；
- GORM；
- CGO SQLite 驱动；
- 微服务；
- Redis/RabbitMQ/Kafka；
- 第三方 Actor/FSM 框架；
- 完整 Event Sourcing；
- 对局跨重启恢复；
- Web 管理后台或管理 API；
- OpenAI 兼容 LLM 或其他 AI 模型接入；
- HTML ParseMode；
- 本机 Docker 镜像构建；
- 应用内置 S3/WebDAV/rclone 备份逻辑；
- 完整 Prometheus/ELK/OpenTelemetry 平台。

## 16. 有意延后的决策

以下事项不阻塞 MVP，在出现明确需求或确定生产环境后再选型：

- 最终生产服务器与操作系统；
- Webhook 是否实际启用及其公网入口；
- 生产备份频率、保留周期、压缩、加密与远端目标；
- AI 模型供应商、提示词、角色策略、成本与超时；
- 完整监控平台；
- 观战、完整回放和 AI 陪练的扩展技术；
- SQLite 连接池上限与同步级别的最终参数；
- 第三方依赖的精确补丁版本。
