# 开发指南

面向新开发者的从零到「可运行、可测试」指南。玩法与架构权威来源见
[游戏流程设计.md](游戏流程设计.md)、[技术选型.md](技术选型.md) 与
[阶段消息设计.md](阶段消息设计.md)；本文只描述工程实践，不修改权威规则。

## 1. 环境要求

- Go 1.25.x：`go.mod` 声明 `go 1.25.13`，CI（`actions/setup-go` 的
  `go-version-file: go.mod`）与 Dockerfile builder 均以此为准。
- 工具经 `go.mod` 的 `tool` 指令固定，用 `go tool <name>` 调用：

  | 工具 | 版本 | 用途 |
  |---|---|---|
  | golangci-lint | v2.12.2 | 静态检查（`make lint`） |
  | sqlc | v1.30.0 | 查询代码生成（`make sqlc`） |
  | govulncheck | v1.7.0 | 依赖漏洞扫描（`make vuln`） |

- 本机 linux/arm64 已知限制（CI amd64 无此问题，以 CI 为准）：
  - `sqlc` 因 wazero cpuid SIGILL 崩溃，`make sqlc`/`make sqlc-check` 本机不可运行；
  - `go test -race` 需要原生 CGO 工具链，本机 arm64 TSan VMA 受限时不可运行；
  - `govulncheck` 需要网络拉取漏洞库。

## 2. 工程结构

```text
telegram-werewolf/
├── cmd/werewolf/            # 入口（serve / backup 子命令）
├── internal/                # 业务实现
│   ├── app/                 # 装配与生命周期、E2E 场景测试
│   ├── config/              # 配置加载与校验
│   ├── game/                # 规则状态机（发牌/夜间/白天/投票/结算/积分）
│   ├── i18n/                # 多语言文案
│   ├── observability/       # slog 日志（敏感键脱敏）与健康检查 handler
│   ├── outbox/              # Telegram 发送队列（限速/重试）
│   ├── player/              # 玩家概念模型
│   ├── room/                # 房间 manager / actor / 计时
│   ├── storage/             # SQLite、迁移、备份
│   ├── storage/sqlc/        # sqlc 生成代码（勿手改）
│   └── telegram/            # Bot 接入、命令、视图
├── migrations/              # 纯 SQL 迁移（goose，嵌入二进制）
├── queries/                 # sqlc 查询定义
├── assets/                  # 静态资源（角色卡片等，go:embed）
├── deploy/                  # systemd 单元与部署配置示例
├── .github/workflows/       # CI 与 Release 流水线
├── testdata/scenarios/      # E2E 场景（好人胜/狼人胜/平票/重启中止）
├── docs/                    # 权威设计与本组手册
├── Makefile                 # 常用门禁目标
├── config.example.yaml      # 配置示例（复制为 config.yaml）
└── sqlc.yaml                # sqlc 配置
```

## 3. 常用命令

`make` 提供以下目标：

| 目标 | 命令 | 说明 |
|---|---|---|
| `make fmt` | `gofmt -w` | 格式化入口文件 |
| `make vet` | `go vet ./...` | 静态分析 |
| `make test` | `go test ./...` | 全量测试 |
| `make test-race` | `CGO_ENABLED=1 go test -race ./...` | Race 检测（CI race job） |
| `make build` | `CGO_ENABLED=0 go build -o bin/werewolf ./cmd/werewolf` | 本地构建 |
| `make build-all` | 交叉编译 linux/amd64 + linux/arm64 | 发布产物验证 |
| `make generate` | `go generate ./...` | 代码生成入口 |
| `make lint` | `go tool golangci-lint run ./...` | 静态检查 |
| `make sqlc` | `go tool sqlc generate` | sqlc 生成（本机 arm64 不可用，CI amd64 为准） |
| `make sqlc-check` | 生成后 `git diff --exit-code` | 保证 sqlc 输出一致 |
| `make vuln` | `go tool govulncheck ./...` | 漏洞扫描（需网络） |
| `make check` | vet + test + build + lint + 全仓 gofmt + git diff --check | **本地全量门禁** |

命令示例（本机）：

```bash
export PATH=/usr/local/go/bin:$PATH
make check        # 本地全量门禁，合并/推送前必须通过
go test ./...     # 全量回归
make build-all    # linux/amd64 与 linux/arm64 交叉编译
```

## 4. 配置

配置示例见仓库根 [`config.example.yaml`](../config.example.yaml)，启动前复制为
`config.yaml`：

```bash
cp config.example.yaml config.yaml
export TELEGRAM_BOT_TOKEN=123456:your-bot-token   # 必需，且不得写入 YAML/仓库/日志
bin/werewolf serve --config config.yaml
```

- 敏感值只通过环境变量注入：`TELEGRAM_BOT_TOKEN`（必需）、
  `TELEGRAM_WEBHOOK_SECRET`（仅预留，MVP 禁止启用 Webhook）。
- 字段（与 `internal/config` 校验规则一致）：

  | 字段 | 说明 |
  |---|---|
  | `database_path` | SQLite 数据库文件路径 |
  | `update_mode` | 仅支持 `polling`；MVP 禁用 webhook |
  | `health_address` | 健康检查监听地址（如 `:8080`）；空字符串＝禁用 |
  | `log_format` | `text`（开发）\| `json`（生产） |
  | `default_locale` | MVP 仅支持 `zh-CN` |
  | `outbox.*` | 发送限速/超时/重试 |
  | `webhook.enabled` | 必须保持 `false`，否则启动校验失败 |

- CLI 子命令：`werewolf serve [--config <path>]`（默认 `config.yaml`）、
  `werewolf backup --output <path> [--config <path>]`。
- 启动校验由 `config.Validate` 执行：Bot Token 非空、`update_mode` 为 polling、
  `log_format` 仅 text/json、时长为合法 Go duration、`health_address` 必须是
  `host:port`、Webhook 禁用等；失败时明确报错退出。

## 5. sqlc

- 配置：`sqlc.yaml`（engine `sqlite`；schema 为
  `migrations/000001_initial.sql` 与 `migrations/000003_add_room_settings.sql`；
  queries 在 `queries/*.sql`；输出 `internal/storage/sqlc`）。
- 修改 `queries/` 后运行 `go tool sqlc generate`，再运行 `make sqlc-check`
  保证生成结果与提交一致（CI `migration-sqlc` job 执行等价检查）。
- 本机 linux/arm64 因 wazero SIGILL 无法运行 sqlc，以 CI amd64 结果为准。

## 6. 数据库迁移

- `migrations/` 下为纯 SQL 迁移（`000001_initial.sql`、
  `000002_add_user_points.sql`、`000003_add_room_settings.sql`），经
  `migrations/embed.go` 嵌入二进制。
- 应用启动时由 Goose library mode 自动执行全部迁移
  （`internal/storage.Migrate`，在 `app.Build` 阶段调用），无需手动迁移命令。
- 从空库跑迁移的测试：

```bash
go test ./internal/storage -run '^TestInitialMigration$' -count=1
```

## 7. 测试与 Fake Bot API

- 单元与集成测试**不需要真实 Bot Token**：测试使用 `httptest` 搭建
  Fake Telegram Bot API（见 `internal/app`、`internal/room` 等测试），
  可离线跑完整 E2E。
- E2E 场景以 YAML 驱动：`testdata/scenarios/` 下
  `good_win.yaml`（好人胜）、`wolf_win.yaml`（狼人胜）、
  `tie_vote.yaml`（复杂平票）、`restart_abort.yaml`（重启中止），
  由 `internal/app` 的 `TestMVPEndToEnd` / `TestScenarioDataValid` 驱动。
- 常用命令：

```bash
go test ./...                                  # 全量
go test ./internal/app -run TestMVPEndToEnd -v # 多场景 E2E
go test ./internal/storage -run '^TestInitialMigration$' -count=1 # 迁移冒烟
```

## 8. 分支与提交约定

- 阶段功能使用独立分支（如 `feat/p0-room`、`feat/p1-night`）＋ PR 合入
  `main`（实施计划约定）；CI 同时监听 push main 与 PR。
- 提交信息使用语义前缀：`feat:` / `fix:` / `test:` / `docs:` / `ci:` /
  `chore:`，如 `feat: add room creation flow`。
- 合并/推送前本地门禁 `make check` 必须全绿，且不留未提交改动；
  远端以 GitHub Actions 自动 CI 为准（workflow_dispatch 不在常规流程内）。
- 敏感值（Bot Token 等）绝不进入提交与日志；日志由
  `internal/observability` 键驱动脱敏保护，调用方也不得把密钥写入自由文本。
