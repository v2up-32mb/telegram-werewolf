# 部署与运维

覆盖 systemd 原生部署与容器部署两种形态、数据目录、健康检查、备份/恢复、
重启中止语义与日志说明。

## 1. 部署形态总览

- 原生二进制是主交付形式：GitHub Release 提供 `linux/amd64` 与 `linux/arm64`
  压缩包及 `checksums.txt`（见 [技术选型.md](技术选型.md) §14.3）。
- 容器镜像是辅助交付形式：tag 时由 GitHub Actions 用 Buildx 构建
  `linux/amd64`、`linux/arm64` 镜像并推送到
  `ghcr.io/v2up-32mb/telegram-werewolf`。
- 本机开发不构建 Docker；PR 不构建不推送镜像。

## 2. systemd 部署（推荐）

部署单元见 [deploy/systemd/telegram-werewolf.service](../deploy/systemd/telegram-werewolf.service)
（含部署步骤注释），配置示例见
[deploy/config.example.yaml](../deploy/config.example.yaml)。

### 2.1 安装二进制

1. 从 GitHub Release 下载对应架构归档：`telegram-werewolf_<版本>_linux_amd64.tar.gz`
   或 `telegram-werewolf_<版本>_linux_arm64.tar.gz`（归档名模板见 `.goreleaser.yaml`）；
2. 校验 `checksums.txt` 中对应条目；
3. 解压并安装到 `/usr/local/bin/werewolf`。

### 2.2 创建专用非登录用户

```bash
useradd --system --no-create-home --home-dir /nonexistent \
        --shell /usr/sbin/nologin telegram-werewolf
```

### 2.3 放置配置与 Token

```bash
install -d -m 0755 /etc/telegram-werewolf
install -m 0644 deploy/config.example.yaml /etc/telegram-werewolf/config.yaml
install -o root -g telegram-werewolf -m 0640 /dev/null \
        /etc/telegram-werewolf/telegram-werewolf.env
echo 'TELEGRAM_BOT_TOKEN=xxx' >> /etc/telegram-werewolf/telegram-werewolf.env
```

Token 只经 `EnvironmentFile` 注入，不写入 unit、仓库或日志。

### 2.4 安装并启动

```bash
install -m 0644 deploy/systemd/telegram-werewolf.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now telegram-werewolf
systemctl status telegram-werewolf
journalctl -u telegram-werewolf -f
```

### 2.5 单元安全与目录语义（与 unit 文件一致）

- `User/Group=telegram-werewolf`：非 root 专用用户；
- `StateDirectory=telegram-werewolf` ＋ `StateDirectoryMode=0700`：
  systemd 自动创建 `/var/lib/telegram-werewolf` 并授权服务用户；
- `ReadWritePaths=/var/lib/telegram-werewolf`：**仅该 SQLite 数据目录可写**，
  其余系统目录只读（`ProtectSystem=strict`、`NoNewPrivileges=true`、
  `PrivateTmp=true` 等）；
- `UMask=0077`：新建文件仅属主可读写；
- `Restart=on-failure`：异常退出自动重启。

## 3. 容器部署

```bash
chown 65532:65532 /var/lib/telegram-werewolf   # 容器以 nonroot（UID 65532）运行
docker run -d --name telegram-werewolf \
  --restart unless-stopped \
  -v /var/lib/telegram-werewolf:/data \
  -e TELEGRAM_BOT_TOKEN=xxx \
  ghcr.io/v2up-32mb/telegram-werewolf:v0.1.0
```

- 镜像基于 distroless static，非 root、无 shell；
- SQLite、配置与日志全部走外部挂载 `/data`（`/data/config.yaml` 提供配置），
  不写入镜像层；
- 挂载目录必须允许 UID 65532 写入。

## 4. 数据目录与 SQLite

- systemd 形态：`/var/lib/telegram-werewolf`（唯一写目录），数据库默认
  `werewolf.db`（`deploy/config.example.yaml` 的 `database_path`）；
- 容器形态：挂载的 `/data`；
- SQLite 使用 WAL 模式，数据目录会同时出现 `werewolf.db-wal` 与
  `werewolf.db-shm`；备份与恢复时注意与主库文件一起处理（见下）。

## 5. 健康检查

配置 `health_address: ":8080"`（空字符串＝禁用）后暴露：

| 路径 | 行为 |
|---|---|
| `/healthz` | 恒 200，表示进程存活 |
| `/readyz` | 顺序执行全部检查项：任一失败即短路返回 503 并列出失败项；全部通过返回 200 |

示例：

```bash
curl -fsS http://127.0.0.1:8080/healthz   # ok
curl -fsS http://127.0.0.1:8080/readyz    # ready
```

## 6. 备份与恢复

### 6.1 备份

```bash
bin/werewolf backup --output /var/backups/telegram-werewolf.db \
                    --config /etc/telegram-werewolf/config.yaml
```

- 从配置读取 `database_path`，生成 SQLite 一致性快照并做完整性校验；
  成功输出 `backup written to <path> (integrity ok)`；
- 建议在执行前记录版本号；备份调度与远端备份目标属生产发布前开放前置
  （MVP 不内置备份调度）。

### 6.2 恢复

1. 停止服务：`systemctl stop telegram-werewolf`；
2. 用备份替换数据文件，并同时移除可能残留的 WAL/SHM 文件：
   ```bash
   install -m 0640 -o telegram-werewolf -g telegram-werewolf \
           /var/backups/telegram-werewolf.db \
           /var/lib/telegram-werewolf/werewolf.db
   rm -f /var/lib/telegram-werewolf/werewolf.db-wal \
         /var/lib/telegram-werewolf/werewolf.db-shm
   ```
3. 启动并验证：`systemctl start telegram-werewolf`，随后检查
   `/readyz` 与日志。

## 7. 重启中止语义（重要）

- 游戏状态**不跨进程重启保留**；Bot 重启后所有进行中的局直接结束，
  并向仍在房间内的玩家发送「游戏结束」通知；
- 中止局**不判胜负、不加减积分、不计入胜负场次**，但保留一条中止记录
  （参与人、时间、原因）供查；
- 因此升级/重启不会造成积分或战绩污染；玩家长期数据（积分/战绩/战报/记录）
  始终持久化在 SQLite。

## 8. 日志

- systemd：`journalctl -u telegram-werewolf -f` 实时查看；
- 生产建议 `log_format: json`，便于采集；
- 日志脱敏：`internal/observability` 对敏感键（`token`、`secret`、
  `password`、`authorization`、`api_key`、`credential` 等，含嵌套
  map/struct/group）递归脱敏为 `***`；
- 边界：脱敏是键驱动的，日志消息文本与自由文本值（如 error 输出）不在
  保护范围内——**不得把密钥放入日志消息或任意文本值**。
